# Benchmark results, 2026-11-07

`Bench-Replication.ps1` with its defaults: 4 servers in a Y (a hub linked to
3 leaves), 5-10 nodes pushing to each, ~200-byte JSON messages, 30 s per
stage, `PeerSyncInterval = 5`, `PeerBatchSize = 100`. All on one machine
(i5-13500, 16 GB, NVMe), PureBasic 5.73 x64 unless said otherwise, SQLite
3.54.1. Table made with `Compare-Runs.ps1`.

PB 6.40 doesn't change them either, SQLite does the scanning.

## What limited each version

- **Before:** the sync to disk on every push, ~250 commits/s per database.
- **WAL + wake-ups:** not the database anymore. The `PrintN()` logging every
  push takes ~0.4 ms and serializes every thread behind it: ~2,400 pushes/s
  per server whatever the number of nodes, with the server mostly idle
  (measured on a single server: the listener asleep in `select()` 91 % of
  the time, the writes busy 33 %, 0.14 ms per push).
- **+ grouping:** same cap, so no gain yet: the pushes never piled up
  behind the write mutex (1.0 per transaction on average). It did cut the
  worst push from 193 to 56 ms.
- **+ no per-push log:** a single server went from ~2,400 to ~12,000
  pushes/s, and grouping now kicks in: 2.5 pushes per transaction at 5
  nodes, ~5-9 at 10-20, the database busy 70-90 % of the time at 0.07-0.11
  ms per push. The cluster tops out at ~25,700 msg/s with the machine at
  67 % CPU (the load generator itself ~85 % of a core). Next limits: each
  server's write section, and running everything on one machine.
- **+ prepared/cache/checkpoints/heads:** ~25,700 -> ~34,300 msg/s. A push
  costs ~0.05 ms of write time instead of 0.07-0.11, no statement is
  prepared again, no MAX() per push. The p99 at moderate load is back under
  1 ms (13.6 -> 0.8 ms at 10 x 50, 18 -> 1.2 ms in the mixed stage): the
  checkpoints were what held the writes up. Flat out, the WAL grows faster
  than the background checkpoints keep up with, so the writer checkpoints by
  itself past 10,000 frames, and the worst push goes from 149 to 854 ms. The
  sync state every check-in reads: 0.5 ms instead of a 167 ms GROUP BY.
- **Same on PB 6.40 C:** ~34,300 -> ~38,400 msg/s (+12 %), the same
  latencies, slightly less lag. Both the servers and the load generator are
  built with it, so part of it may be the generator. The SQLite side (the
  write section, the queries) is the same DLL either way.

## Notes

- Ids checked after the last four runs: every node 1..N, no gap, no
  duplicate, on all 4 servers, and `node_heads` exactly matching `data`.
- **p99 at moderate load went up with grouping** (0.7 -> 8-18 ms), and came
  back down once the checkpoints left the write path (see above).
- Replication keeps up at every load: it drains within ~11 s even after
  38,000 msg/s. The lag is the check-in wait (`PeerSyncInterval`) plus the
  hub relaying to its leaves, see `Design/Suggestions.md` #2 to lower it.
- The worst push flat out (0.85-1.5 s) is the writer's backstop checkpoint,
  see `Design/Suggestions.md` #3.

## Names and wildcards (evening)

Same benchmark, PureBasic 5.73, after topics and nodes got names, strict
"named on both sides" replication, and wildcards, run with `-Names
Wildcard`: each server only names its own nodes, and takes everyone else's
by `AcceptNodes = n*`, so each server adds the other servers' 30 nodes
under ids of its own (counting down from 65535), and the hub relays them on
by name. The worst case for the new code: every batch goes through a name
lookup and every check-in through the patterns. Run `20261107-220433`,
compared with `Compare-Runs.ps1` (`comparison.md` in the run's folder).

- **Same speed, within run-to-run noise.** Flat out at 10 nodes, the same
  build gave 32,976 and 37,003 msg/s in two ramp-only runs (declared names)
  earlier this evening: ±6 % between runs is usual on this machine. The push
  path itself didn't change, only the check-ins and the batches' first
  lines.
- **Server CPU +7 %** flat out (129 vs 120 % of a core), the name lookups
  and the bigger sync states, possibly part of the noise too.
- **Replication** keeps up at every load and drains in the same time; no
  batch refused anywhere, every server ended with the same rows.
- **Measuring changed slightly:** the lag monitor now asks for each node's
  latest id by name through the `messages` view (ids differ between
  servers in this mode), the old runs asked `data` by id. Both are index
  lookups.
